# GitHub и обновления VPS

## Два разных вида изменений

**Товары и заказы** — данные магазина. Изменения цены, фото, состава и наличия через админку сохраняются сразу в SQLite и `data/media`. Если открыта админка на VPS, изменения уже действуют на VPS. GitHub для этого не нужен. Локальная демонстрация на порту 8765 использует отдельную базу и не синхронизируется с VPS.

**Код приложения** — дизайн, кнопки, логика, интеграции. Он хранится в GitHub, проверяется тестами и затем развёртывается на VPS.

Сохранение файла само по себе не отправляет его в GitHub. Обычный цикл: изменить код → проверить → сделать commit → push → автоматические проверки → обновление VPS.

## Что уже подготовлено

- `.gitignore` исключает `.env`, базу, медиа, резервные копии, ключи, журналы и виртуальное окружение.
- `.github/workflows/ci.yml` запускает тесты на Ubuntu с Python 3.11 и 3.13 после push, при pull request и вручную.
- `.gitattributes` сохраняет корректные переводы строк для Windows и Linux.

**Автоматический деплой на VPS пока не подключён.** Для него нужны конкретный репозиторий, адрес сервера, SSH-доступ и проверенные пути установки. Текущий workflow выполняет проверки и не отправляет ничего на сервер.

## Публикация проекта

В корне репозитория должны лежать `app/`, `deploy/`, `tests/`, `.github/` и `requirements.lock.txt`, а не архив и не внешняя папка `outputs`.

Для нового пустого репозитория после выбора его адреса:

```bash
git init -b main
git add .
git diff --cached --stat
git commit -m "Initial Osen Kusna bot and admin"
git remote add origin https://github.com/OWNER/REPOSITORY.git
git push -u origin main
```

`OWNER/REPOSITORY` заменяется реальным адресом. Git должен быть авторизован в нужном аккаунте. Данные авторизации GitHub не записываются в `.env` бота.

## Как будет работать автоматическое обновление

1. Изменение кода отправляется в рабочую ветку GitHub.
2. Тесты проходят в pull request.
3. Изменение попадает в `main`.
4. Задание деплоя, зависящее от успешных тестов, подключается к VPS по SSH.
5. Сохраняется резервная копия базы. Новая версия кода и её окружение готовятся отдельно от работающей версии.
6. Сервисы переключаются на новую версию, перезапускаются и проверяются.
7. Если запуск не удался, возвращается прежний код. Изменения структуры базы требуют отдельного плана совместимости и восстановления.

Рабочие `.env`, SQLite, фото и бэкапы находятся в постоянном каталоге вне сменяемой версии кода. Новый деплой не перезаписывает их. Одновременно работает только один процесс Telegram-бота.

На первом этапе запуск обновления можно сделать вручную из GitHub Actions, а после пробного успешного обновления включить автоматический запуск при push в `main`. Автосохранение каждого незавершённого изменения в рабочую систему не настраивается.

## Какие данные понадобятся для подключения

| Настройка | Назначение |
|---|---|
| Адрес репозитория и рабочая ветка | Откуда получать код |
| IP или домен VPS, SSH-порт | Куда подключаться |
| SSH-пользователь деплоя | Кто обновляет приложение |
| Отдельный SSH-ключ деплоя | Закрытая часть — в GitHub Actions Secrets, открытая — на сервере |
| Проверенный SSH host key сервера | Проверка подлинности VPS при подключении |
| ОС, путь проекта и пути постоянных данных | Настройка установки и сохранности базы |

Закрытый ключ не вставляется в YAML workflow. Секреты бота остаются на VPS: для доставки кода Actions не нужен Telegram-токен или содержимое базы.

GitHub позволяет запускать workflows по событиям push и pull request, ограничивать права токена и хранить данные подключения в Secrets. См. [Python в GitHub Actions](https://docs.github.com/en/actions/tutorials/build-and-test-code/python), [настройка деплоя](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments), [секреты Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).
